## 1. Rôle réel de ce qui a été audité

- **Base de production** lue au canal ① (outil MCP `execute_sql`, rôle `supabase_read_only_user`, `transaction_read_only = on`, PG 17.6). Ce rôle a `rolbypassrls = true` et n'est **pas** membre d'`anon`/`authenticated` : `SET LOCAL role authenticated` est **refusé** (`42501 permission denied to set role`). L'évaluation « sous rôle » s'est donc faite en posant les claims (`set_config('request.jwt.claims', …)` dans le même appel → `auth.uid()`/`auth.role()` répondent bien) **et en appliquant moi-même le prédicat de chaque policy** lu dans `pg_policies`, puisque la RLS n'est pas opposée à ce rôle. C'est une évaluation de la *logique* des policies sur les données réelles, pas une exécution sous le rôle PostgREST : je le dis partout où ça compte. Les bancs SQL locaux (42 + 1 nouveau), eux, exécutent les vraies policies sous les vrais rôles `anon`/`authenticated` sur un PostgreSQL 16 jetable.
- **Aucun compte de test `%@passio-e2e.test`** en base (14 `auth.users`, tous réels, 1 non confirmé). L'évaluation « membre » a utilisé un uid synthétique inexistant (`00000000-0000-4000-8000-000000000001`) : elle prouve ce qu'un **non-membre / non-propriétaire** voit (c'était la question), pas ce qu'un vrai membre voit.
- **Aucune écriture en production**, aucune écriture de test en base. Les correctifs sont deux fichiers du dépôt (migration + banc), prouvés localement, **non appliqués** (contre-revue humaine exigée par le dépôt).
- Environnement : Supabase REST/Edge injoignables depuis le shell (confirmé par le brief) → aucun appel RPC réel ; les comportements des fonctions ont été établis par lecture du corps (`pg_get_functiondef`) et par exécution des **prédicats** sur les données.
